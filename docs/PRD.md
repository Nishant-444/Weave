# PRD: PDF & CSV RAG System

**Owner:** Nishant

---

## 1. Goal

Build a production-quality, end-to-end RAG system that ingests PDFs and CSVs, organizes them into named **collections**, answers questions with **deterministic citations**, handles **tabular aggregation queries correctly**, and **proactively surfaces key metrics/insights** on a dashboard - without relying on RAG frameworks (LangChain/LlamaIndex).

Supabase's free tier runs indefinitely (not a trial) and needs no card. All DB access goes through a thin, hand-written `asyncpg`/`psycopg` layer - no Supabase SDK, no ORM - so swapping to Neon or self-hosted Postgres later is a config change, not a rewrite.

## 3. Core Concepts

### 3.1 Collections (multi-tenancy)

Every uploaded document belongs to a named **collection** (e.g. "Vyntics"). This is the top-level namespace across the whole system.

- Every table (`chunks`, per-CSV tables, `insights`) includes a `collection_id` column
- Vector search filters on `collection_id` via a normal `WHERE` clause alongside the pgvector similarity operator
- Retrieval, chat, and dashboard are always scoped to the active collection
- Frontend: collection switcher (dropdown/sidebar) controls what's visible

### 3.2 Deterministic PDF Citations

Citations are **never generated by the LLM** - they are mechanically attached from the retrieval step (page number, snippet, offset), so they cannot hallucinate.

### 3.3 Smart CSV Handling

Two parallel representations per CSV:

- **Row-to-text**: each row serialized into a natural-language sentence, embedded, stored in the `chunks` table's pgvector column → handles semantic/lookup questions
- **Raw SQL table**: loaded into its own typed Postgres table → handles aggregation questions ("average", "total", "top N") via LLM-generated SQL, executed for real numbers (no hallucinated math)

A lightweight query router (LLM classification: semantic vs. aggregation) decides which path a question uses.

### 3.4 Proactive Insight Extraction

After ingestion, a single structured-output extraction pass scans each document for metrics/KPIs/facts and stores them as `{metric, value, page, snippet, collection_id}`. Rendered as dashboard cards, each still citation-linked. This runs automatically - not on-demand.

### 3.5 Full-Text Rendering

Users can view the complete extracted text of any uploaded PDF (by page), not just chat with it. Required for the "any PDF, render all its text" requirement at ~10k-line scale.

## 4. Data Flow

### PDF Ingestion Pipeline

1. Upload PDF → assign `document_id`, `collection_id`
2. PyMuPDF extracts text per page
3. Chunk per-page text (~500 tokens, small overlap), each chunk tagged `{page_num, source_file, char_offset, collection_id}`
4. Batch-embed chunks (not one-by-one - required at 10k-line scale for speed)
5. Store in Postgres: embedding in a pgvector column, metadata in normal typed columns
6. Run insight-extraction pass → store results in `insights` table
7. Emit SSE progress events: `parsing → chunking → embedding → extracting_insights → done`

### CSV Ingestion Pipeline

1. Upload CSV → assign `document_id`, `collection_id`
2. Pandas loads and validates the file
3. Path A: serialize each row to natural language → batch-embed → store in `chunks` (pgvector column)
4. Path B: load raw table into its own typed Postgres table, tagged `collection_id`
5. Emit SSE progress events

### Query Flow

1. User asks question, scoped to active `collection_id`
2. Router classifies: semantic lookup vs. aggregation
3. **Semantic** → vector retrieval (top-k) → LLM answers using only retrieved chunks → citations attached from metadata
4. **Aggregation** → LLM generates SQL against known schema → executes on Postgres → LLM formats the real result
5. Response streamed token-by-token via SSE
6. Citation badges rendered inline, clickable → opens source page/snippet

## 6. Data Schema (draft)

**Postgres tables (single database, pgvector extension):**

- `documents(id, collection_id, filename, type, uploaded_at, status)`
- `chunks(id, document_id, collection_id, source_file, type: "pdf"|"csv_row", page_num, char_offset, embedding vector(384))` - `embedding` is a native pgvector column, indexed (ivfflat/hnsw) for fast similarity search
- `insights(id, document_id, collection_id, metric, value, page_num, snippet)`
- One dynamically-created table per CSV, prefixed by `collection_id` + `document_id`, used for raw SQL aggregation

All access goes through a thin, hand-written data layer (`asyncpg`/`psycopg`, raw SQL) - no ORM, no Supabase client SDK - so every query is visible and the DB provider is swappable.

## 7. Frontend Requirements

- Two-pane dashboard: ingestion zone (left) + chat (right)
- Collection switcher
- Ingestion zone: drag-drop, per-file progress bar with named stages
- Insights cards: auto-populated metric cards, citation-linked
- Full-text viewer: page-by-page PDF text view
- Chat: token-streaming responses, inline citation badges, click-to-source
- Robust empty/error/loading states throughout

---

## 8. Non-Functional Requirements

- Strict typing: Pydantic models (backend), TypeScript interfaces (frontend) - no `any`/untyped dicts crossing boundaries
- Error handling: every ingestion/query step wrapped, user-facing error states (not raw stack traces)
- Decoupled architecture: ingestion, retrieval, and generation are separate modules, independently testable
- No framework abstractions for chunking/retrieval/routing - all hand-written and explainable
- Provider fallback: Gemini → Groq swap via config, not hardcoded
- No vendor lock-in: plain SQL + a standard Postgres driver only - Supabase, Neon, or self-hosted Postgres are interchangeable via one connection string

## 12. Strategic Alignment Notes

Context for framing decisions with the founders - not build instructions.

- **Stack mirrors production**: FastAPI + Postgres is what Vyntics already runs. Continuous with their real codebase, not a demo hack.
- **Citations are their identity**: their shipped compliance RAG product is built entirely around verified, audit-ready answers. Section 3.2 is the non-negotiable core, not a nice-to-have.
- **Insights = their named service pillar**: "Insight Engineering" is one of Vyntics' three core offerings. Section 3.4 should lead the demo, not trail it.
- **Flagged as future work - mention in README, don't build in 72h**:
  - Hybrid search (keyword + vector) - present in Vyntics' shipped product
  - Redis-backed job queue, replacing the in-memory dict, for concurrent ingestion at scale
  - Swap path to Neon or Pinecone if scale demands it - enabled by the portable SQL layer (Section 8)
