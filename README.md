## Project Overview

**Weave** is an enterprise-grade, framework-free Retrieval-Augmented Generation (RAG) and document intelligence platform engineered for high accuracy across both unstructured documents (complex multi-page PDFs) and structured tabular datasets (CSVs).

Built without bloated orchestration wrappers (no LangChain or LlamaIndex), Weave solves the two largest problems in enterprise document AI: **arithmetic hallucination over tabular data** and **unreliable/hallucinated citations**.

### Key Architectural Highlights

- **Deterministic Non-Hallucinated Citations**: Citations are derived strictly from database retrieval and query execution provenance—never generated by the LLM prompt. Every citation links to an exact PDF page number, character offset, CSV row, or executed SQL query.
- **Dual-Path CSV Ingestion & Execution**:
  - **Path A (Semantic Search)**: Row-to-text serialization embedded into 384-dimensional dense vectors in `pgvector` for qualitative/semantic questions.
  - **Path B (Live SQL Aggregation)**: Type inference automatically parses currencies (`$1,304.12`, `-$81.55`), percentages (`24.08%`), numbers, and dates into dynamic typed PostgreSQL tables (`csv_doc_<doc_id_hex>`) for exact mathematical aggregations (`SUM`, `AVG`, `ROUND`, `GROUP BY`).
- **Hybrid Structural Search with Tesseract OCR Fallback**:
  - Captures document structure (Title, Front-matter, Table of Contents) ensuring accurate answers to macro-level queries (*"who is the author"*, *"list all chapters"*).
  - High-resolution **Tesseract OCR fallback** for scanned pages, infographics, diagrams, and non-selectable image text.
- **Dual-Provider LLM Resilience Layer**:
  - Primary provider: Google Gemini (`gemini-3.6-flash`).
  - Automatic pre-stream failover to Groq (`openai/gpt-oss-120b` / `llama-3.3-70b-versatile`) upon rate limits (`429`, `RESOURCE_EXHAUSTED`).
- **Multi-Tenant Collections**: Complete data isolation across collections—every table, chunk, and dynamic SQL table is partitioned by `collection_id`.
- **Real-time Server-Sent Events (SSE)**: Full token-by-token streaming and live multi-stage ingestion progress tracking (`parsing` → `chunking`/`storing` → `embedding` → `done`).
- **Minimalist Modern Frontend**: Built with React 18, TypeScript, Vite, Tailwind CSS, and shadcn/ui. Includes full-text PDF viewer, CSV tabular preview, token-streaming chat, and an interactive citation inspection drawer.

## Database Schema & Multi-Tenancy

The database is built on PostgreSQL with strict relational integrity and multi-tenant partitioning by `collection_id`. All schema DDL migrations run automatically on startup.

```
┌─────────────────┐       ┌─────────────────┐       ┌─────────────────┐
│   collections   │ 1───N │    documents    │ 1───N │ document_pages  │
└─────────────────┘       └─────────────────┘       └─────────────────┘
                                   │ 1                       │
                                   ├─────────N───────────────┤
                                   │                         ▼
                                   │                ┌─────────────────┐
                                   │                │     chunks      │ (pgvector 384-dim)
                                   ▼                └─────────────────┘
                          ┌─────────────────┐
                          │   csv_tables    │
                          └─────────────────┘
                                   │ 1
                                   ▼
                          ┌─────────────────┐
                          │ csv_doc_<id>    │ (Dynamic Typed SQL Table)
                          └─────────────────┘
```

### Core Relational Tables

1. **`collections`**: Tenant isolation namespace.
   - `id` (UUID, Primary Key)
   - `name` (TEXT, Unique)
   - `description` (TEXT)
   - `created_at` (TIMESTAMPTZ)
2. **`documents`**: Parent record for uploaded PDF/CSV files.
   - `id` (UUID, Primary Key)
   - `collection_id` (UUID, Foreign Key → `collections.id` ON DELETE CASCADE)
   - `filename` (TEXT)
   - `file_type` (TEXT: `'pdf'` | `'csv'`)
   - `total_pages` / `row_count` (INT)
   - `created_at` (TIMESTAMPTZ)
3. **`document_pages`**: Page-level full text for PDF document inspection.
   - `id` (UUID, Primary Key)
   - `document_id` (UUID, Foreign Key → `documents.id` ON DELETE CASCADE)
   - `page_number` (INT)
   - `page_text` (TEXT)
4. **`chunks`**: Vector table storing dense text representations.
   - `id` (UUID, Primary Key)
   - `document_id` (UUID, Foreign Key → `documents.id` ON DELETE CASCADE)
   - `collection_id` (UUID, Foreign Key → `collections.id` ON DELETE CASCADE)
   - `chunk_index` (INT)
   - `chunk_type` (TEXT: `'pdf_chunk'` | `'csv_row'`)
   - `content` (TEXT)
   - `embedding` (`vector(384)`, Indexed via `HNSW` with Cosine distance `<=>`)
   - `metadata` (JSONB: `page_num`, `char_offset`, `row_num`, `is_toc`, `is_front_matter`)
5. **`csv_tables`**: Registry of dynamic SQL aggregation tables.
   - `id` (UUID, Primary Key)
   - `document_id` (UUID, Foreign Key → `documents.id` ON DELETE CASCADE)
   - `collection_id` (UUID, Foreign Key → `collections.id` ON DELETE CASCADE)
   - `table_name` (TEXT: `csv_doc_<doc_id_hex>`)
   - `column_definitions` (JSONB: column names and inferred SQL types)
6. **`csv_doc_<id_hex>`**: Dynamic typed PostgreSQL tables generated per CSV file with clean headers, numeric precision, and sanitized column types.

## Technical Decisions & Trade-offs

### Why Framework-Free over LangChain or LlamaIndex?
- **Zero Abstraction Overhead:** LangChain and LlamaIndex introduce thick wrapper layers, brittle prompt templates, and opaque dependency trees that degrade debugging and increase latency.
- **Full Asyncpg & Connection Control:** Writing directly against `asyncpg` allowed fine-grained connection pooling, explicit transaction boundaries, and `statement_cache_size=0` optimization for Supabase/PgBouncer poolers.
- **Transparent LLM Failover:** Implementing failover logic directly ensures clear pre-stream interception of `429` / `RESOURCE_EXHAUSTED` errors without obscure framework retry exceptions.

### Why Dual-Path (Vector Search vs. Dynamic SQL Aggregation) for CSVs?
- **The Problem with Vectorizing Tables:** Embedding tabular rows as text strings causes LLMs to hallucinate math. An LLM reading 50 chunk snippets cannot reliably compute `SUM("Revenue")` or `AVG("Operating Margin")`.
- **The Dual-Path Solution:**
  - **Path A (Semantic Search):** Serializes rows into key-value text to answer qualitative lookups (*"What does company X specialize in?"*).
  - **Path B (Text-to-SQL Execution):** Infers SQL types, creates a physical PostgreSQL table, generates standard SQL queries (`SELECT`, `SUM`, `GROUP BY`), and executes them in database. Math is 100% computed by PostgreSQL with zero LLM calculation hallucination.

### Why PostgreSQL + pgvector over Pinecone / ChromaDB?
- **Zero Separate Database Containers:** `pgvector` runs directly inside PostgreSQL. This eliminates running a separate vector database container, saving hundreds of megabytes of RAM.
- **Relational Integrity:** Document metadata, collections, chunks, and dynamic SQL tables share the same database instance. Cascading deletes (`ON DELETE CASCADE`) keep relational data synchronized without orphan vector vectors.
- **Single Source of Truth:** SQL aggregation queries and vector distance similarity searches operate against the same unified database.

### Why Dual-Provider LLM Resilience (Gemini 3.6 Flash -> Groq)?
- **High Availability Under Quota Limits:** Free-tier or standard LLM APIs frequently throw `429 Too Many Requests` during burst traffic.
- **Seamless Failover:** If Gemini returns a rate-limit error, the resilience layer catches the exception before opening the SSE stream, seamlessly switching the request to Groq (`openai/gpt-oss-120b` or `llama-3.3-70b-versatile`) with zero user interruption.

### Why Local sentence-transformers (`all-MiniLM-L6-v2`)?
- **Zero Embedding API Costs:** Embedding 1,000+ CSV rows or 700-page textbooks via paid APIs creates recurring latency and API costs.
- **Lightweight & Fast:** At ~90MB, `all-MiniLM-L6-v2` runs efficiently on standard CPUs, producing high-quality 384-dimensional dense vectors in batch without GPU requirements.

### Why Astral `uv` over standard `pip` / `venv`?
- **10-100x Faster Resolution:** Built in Rust, `uv` installs dependencies and PyTorch CPU in seconds rather than minutes.
- **Deterministic Lockfile (`uv.lock`):** Guarantees zero version drift between local dev environments and Docker production images.
- **Native CPU PyTorch Index Mapping:** Configured in `pyproject.toml` with `[tool.uv.sources]` to explicitly pull lightweight CPU-only PyTorch wheels (~150MB instead of ~2GB CUDA binaries).

## Security Implementation & Guardrails

### Safe Text-to-SQL Execution Sandbox
1. **Keyword Sanitization & Whitelisting:**
   - Generated SQL queries are strictly validated. Queries containing mutating keywords (`DROP`, `DELETE`, `INSERT`, `UPDATE`, `ALTER`, `TRUNCATE`, `CREATE`, `GRANT`, `REVOKE`) are immediately rejected.
   - Enforces that queries must start with `SELECT` or `WITH`.
2. **Read-Only Scoping:**
   - Queries execute against dynamically introspected schema names registered in `csv_tables`.
3. **Multi-Tenant Isolation:**
   - All vector lookups, document queries, and SQL table lookups are explicitly scoped to the active `collection_id`.
4. **Environment & Secret Protection:**
   - API keys and database URLs are loaded strictly via Pydantic `BaseSettings` (`SecretStr`) and excluded from logs and version control.

## Known Limitations & Roadmap

### Current Constraints
1. **Single-Node Ingestion:** Ingestion runs asynchronously in FastAPI background tasks; large multi-GB batches would benefit from a dedicated Celery/Redis queue.
2. **Single-Table SQL Queries:** Text-to-SQL currently operates across tables in the same collection; cross-document SQL joins are planned.
3. **Local Embedding CPU Bounds:** Embeddings run locally on CPU; cold starts take ~2-3 seconds for model loading.

### Planned Enhancements (v2.0)
- Cross-encoder re-ranking (`FlashRank` / `bge-reranker-small`) for refined top-k precision.
- Celery + Redis distributed worker task queue for massive multi-document bulk ingestion.
- Hybrid BM25 + dense vector reciprocal rank fusion (RRF).
- User authentication with Supabase Auth / Clerk and Row-Level Security (RLS).
